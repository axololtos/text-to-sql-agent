Automated SQL Execution Self-Correction & Repair Loop

When a generated query fails against the database, the exact engine error is captured, fed back into the agent's context with an explicit instruction to fix it, and retried — bounded to a configurable budget so a broken query can't loop forever.

built 2026-09-04 python · langchain create_agent model: gemini-3.6-flash db: chinook.db (sqlite, 11 tables)

What changed

LangChain's agent loop already round-trips tool errors back to the model, and the system prompt already told it to retry. What was missing was a ceiling. The change wraps the toolkit's sql_db_query tool in a small counter: successful results pass straight through and reset the count; a result beginning Error: increments it and gets an instruction appended; once the count hits --max-repair-attempts (default 3) the wrapper returns a terminal instruction telling the agent to stop rewriting and report the last error verbatim. A recursion_limit of 6 · n + 12 on the invoke call is the backstop against spinning on the other tools.

How the loop runs

  1. Model writes a queryThe agent drafts SQL and calls the wrapped sql_db_query tool.
  2. Engine rejects itSQLite returns an error string; the underlying tool hands back Error: (sqlite3.OperationalError) no such column: Employee.salary.
  3. Wrapper captures & countsThe Error: prefix is detected, the failure counter goes to 1, and the raw error is returned to the model with an instruction attached. [self-correction 1/2] Read the error above, fix the query, and call sql_db_query again.
  4. Model tries againIt rewrites the query from the error text. If this one succeeds, the counter resets to zero and the run continues normally.
  5. Budget reachedOn the 2nd failure the counter meets the limit, so instead of another retry prompt the wrapper returns a stop instruction. [repair budget exhausted after 2 failed attempts] Stop rewriting the query. Report the error above to the user verbatim as your final answer.
  6. Agent reports outThe model stops calling the tool and returns the database error as its answer — no infinite loop, no silent failure.

Decisions worth defending

Wrap the existing tool, don't replace the agent. A custom LangGraph loop would re-implement error round-tripping the framework already does. The wrapper is ~25 lines and leaves create_agent and the rest of SQLDatabaseToolkit untouched.
Count failures, not tool calls. The counter only moves on an Error: result and resets on any success, so a query that fails once then works isn't penalised later in the same run.
Detect errors by the tool's own contract. The community sql_db_query tool returns db.run_no_throw() output — errors arrive as strings prefixed Error:, never as exceptions. The wrapper keys off that instead of adding a second execution path.
Two guards, not one. The failure counter bounds SQL repair; the recursion_limit bounds everything else, so the agent can't dodge the cap by thrashing on schema lookups.
